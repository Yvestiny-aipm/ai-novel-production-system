## 3. 五场真实模型主链路

`real_test_rerun_25.db` 中每场均按以下隔离链路执行：

```text
ContextPack → planning/ScenePlan → writing/ProseDraft
→ review_world + review_plot + review_style → QualityReport
→ memory_extraction/MemoryProposal
```

恢复与不可覆盖的自动测试验证：

- 已完成第 1 场恢复时零新增 Harness 调用；正文 hash、提案、审批和记忆完全保持。
- 中间节点异常恢复时，已保存 ScenePlan 不重做，恢复从 writing 继续。
- 同编号同内容可复用；同编号不同内容被拒绝。ScenePlan、ProseDraft、QualityReport、MemoryProposal、memory_records 不使用覆盖式写入。
- 明确返工才生成新版本；历史 draft、report、proposal 及审批来源均保留。

## 8. TaskState 前端语义

`status` 是前端判断任务是否完成、等待、阻塞或排队的唯一生命周期依据。

- `status=completed`：任务已经完成。
- `status=waiting_confirmation`：任务等待人工动作。
- `status=blocked` 或 `exception_pending`：任务不能自动继续，需按原因处理。
- `current_node` 记录当前业务节点；当 `status=completed` 时，它可以保留最后处理节点，例如 `human_confirmation` 或 `memory_processing`。

因此，前端不得只根据 `current_node=human_confirmation` 显示“处理中”。当前展示应为“已完成（最后节点：human_confirmation）”。

## 9. 真实失败类型与修复结果

| 类别 | 真实/回归现象 | 修复与当前处理 |
| --- | --- | --- |
| Contract type 混淆 | 内部 `scene_generation` 曾被误作 ScenePlan Contract | 内部 task type 与业务 `contract_type=ScenePlan` 明确分离 |
| 非 JSON 或错误包络 | DeepSeek 输出可能带围栏或说明文字 | OpenAI 兼容内容解析、围栏提取及严格 envelope 校验 |
| 审查职责混淆 | 审查员曾直接输出不完整 QualityReport | 审查员输出 ReviewerResult，后端汇总完整 QualityReport |
| 不完整场景状态 | `reviewed=true` 或空状态曾进入后续链路 | 必须有六类真实 state 字段，否则 Contract 无效 |
| 记忆枚举/权限 | 旧值、错误 write_policy 或非法 action | 固定类型—范围—策略映射，Harness 严格拒绝 |
| 缺 target_key | `resume_32` 第 2 场真实响应漏字段 | 保持必填，不自动补造；提示词强化，脱敏真实样本回归 |
| 恢复覆盖历史 | 异常恢复可能重跑/替换既有结果 | 不可变插入、版本化返工、检查点恢复和基线对比 |
