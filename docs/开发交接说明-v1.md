## 一、项目目标

这是一个公司内部使用的长篇小说生产系统，目标是稳定、自动化、可追溯、可恢复地规模化生产长文小说。

第一版生产单位是“场”：

- 每场目标约 1250 字
- 建议允许范围 1000～1500 字
- 每章两场
- 目标作品约 80 章、20 万字
- 第一版不接入 n8n

系统首先验证全链路稳定性，再进行长篇规模测试。

## 二、已确认的总体架构

```text
创作工作台 / 管理后台
          ↓
统一后端（唯一流程控制中心）
  ├─ 规划 Agent
  ├─ 生文 Agent
  ├─ 审查 Agent
  │    ├─ 世界规则和前后设定审查员
  │    ├─ 人物行为和剧情结构审查员
  │    └─ 语言表达和阅读体验审查员
  ├─ 按需：裁决 Agent
  ├─ 记忆 Agent
  ├─ Harness（模型调用管理）
  │    └─ 模型接口适配器（供应商差异转换）
  └─ 上下文与数据管理
       ├─ 资料库
       ├─ 检索
       ├─ ContextPack 组装
       ├─ 版本管理
       └─ 写入权限控制
```

核心原则：

> Harness 负责模型调用管理，模型接口适配器负责供应商差异转换；Agent 只提出任务请求，统一后端控制流程，上下文与数据管理控制资料和写入权限。

其他边界：

- Agent 不直接调用其他 Agent。
- Agent 不直接调用具体模型 API。
- Agent 不直接访问数据库。
- Agent 不直接修改 TaskState。
- Agent 不直接修改正式世界规则。
- 前端不直接访问 Agent、Harness 或数据库。
- 所有业务流程由统一后端控制。

## 三、核心主链路

```text
CreativeBrief 确认
  → 规划 Agent
  → 组装当前 ContextPack
  → 生文 Agent
  → 三位审查员审查
  → 审查通过：记忆 Agent 提取提案
  → 记忆系统检查并按权限写入
  → 当前场次完成
  → 下一场使用已确认的上一场状态
```

审查不通过时：

```text
普通局部问题（≤10个）
  → 生文返工

普通问题超过10个
  → 升级为严重问题
  → 裁决 Agent

普通问题但影响其他场或章节
  → 裁决 Agent

三位审查员对同一事实或行动给出相反结论
  → 真正冲突
  → 裁决 Agent

正文第一次、第二次失败
  → 生文返工

正文第三次失败
  → 规划返工

规划返工后仍失败
  → 场次阻塞
  → 默认暂停整部小说
```

## 四、七类固定业务 Contract

第一版固定七类业务交接内容：

1. `CreativeBrief`：作品级创作起始资料
2. `ScenePlan`：场次规划卡
3. `ContextPack`：指定 Agent 使用的固定资料快照
4. `ProseDraft`：场景正文草稿
5. `QualityReport`：审查报告
6. `MemoryProposal`：记忆变更提案
7. `TaskState`：任务运行状态

模型请求和响应属于 Harness 内部记录，不增加第八类业务 Contract。

### 1. CreativeBrief

作品级、版本化、确认后只读。

固定内容：

- 作品名称
- 作品类型
- 故事主题
- 目标篇幅
- 主要人物
- 人物关系
- 世界背景
- 核心规则
- 主要冲突
- 风格要求
- 结局方向
- 用户特别要求

规则：

- 确认后不能直接修改。
- 任何修改都创建新的 `brief_version`。
- 新版本确认后暂停受影响的创作任务。
- Agent 无权修改。

## 五、最终状态规则

### 暂停、阻塞、完成

- `paused`：可以继续，只是等待用户、人工或系统处理。
- `blocked`：无法继续，必须解决问题或确认跳过。
- `completed`：正文审查通过，且记忆处理完成。
- 记忆提案等待人工确认时，任务保持 `waiting_confirmation`。
- 人工拒绝记忆提案后，正文任务可以完成，提案状态为 `rejected`。

### 异常

```text
原业务节点运行中
  → exception_pending
  → exception_handling
  → 回到原节点继续，或进入 paused / blocked
```

技术异常不能直接计为内容失败，也不能直接跳过业务节点。

### 跳过场次

只有用户明确确认后才能跳过。必须记录：

- 跳过原因
- 确认人
- 被跳过场次原本承担的剧情功能
- 下一场需要注意的连续性缺口

下一场 ContextPack必须带入这份缺口记录。

### 返工次数

- 字数失败：只回生文；同一 Plan 最多 4 份长度 Draft，第 4 份仍失败则阻塞，不回规划
- 剧情内容第一次失败：生文返工
- 剧情内容第二次失败：生文返工
- 剧情内容第三次失败：规划返工
- 新内容规划周期后再失败：阻塞

`plan_version` 是计划版本号，每生成一份新计划就递增，包括规划自身修错。`plan_attempt` 是正文内容规划周期，初始为 1，只有正文累计三次剧情内容失败、正式返回 Planning 时才变成 2。字数失败和规划质量返工都不增加 `plan_attempt`，两者不能当成同一个数字。

TaskState 的 `content_attempt_in_plan` 记录当前内容规划周期下的剧情内容失败次数；`content_attempt_total` 记录整场剧情内容失败累计次数。字数失败不改变这两个数字。正式进入新的正文内容规划周期后，当前规划次数重新计算，但历史累计次数不能删除。规划质量返工不增加这两项计数。ProseDraft 上的同名字段只表示该场 Draft 生成顺序，不得用来覆盖或改写历史 Draft，也不能当成 TaskState 失败计数。

## 六、数据库逻辑结构

第一版使用一个关系型数据库，不拆多个数据库。

逻辑表：

```text
books
chapters
scenes
creative_briefs
scene_plans
context_packs
prose_drafts
quality_reports
memory_proposals
task_states
task_events
exception_queue
harness_calls
memory_records
```

数据库边界：

- `QualityReport.accepted_scene_state`保存历史确认记录。
- `scenes.current_scene_state`保存当前快捷投影，并记录来源 `report_id`。
- `QualityReport`是历史证据，`scenes`是当前读取入口。
- `books.current_brief_version`和`books.current_canon_version`只是快捷指针。
- `memory_records`统一保存场景记忆、作品专属资料、公共图书馆资料和正式世界规则。
- 三位审查员结果先放在 `quality_reports.reviewer_results`结构化字段中。
- ContextPack检索来源先放在固定快照中，暂不单独建立检索明细表。
- 正文第一版直接保存为数据库 `TEXT`。

必须落实的数据库约束：

- 同一作品同一场只能有一个运行中的任务。
- 同一业务对象内版本编号唯一。
- QualityReport只能绑定一个确定的正文版本和正文哈希。
- ContextPack生成后不可修改。
- 正式记忆写入必须有审批状态。
- TaskEvent只允许新增。
- `idempotency_key`唯一。
- 状态变更、版本创建和关联关系在同一事务内完成。

## 七、接口方案

第一版使用 REST + 异步任务。

```text
前端 → 统一后端 → TaskState → Agent → Harness → 模型适配器
```

前端不直接访问 Agent、Harness或数据库。

### 业务命令

```text
POST /api/v1/books
POST /api/v1/books/{book_id}/briefs
POST /api/v1/books/{book_id}/briefs/{brief_version}/confirm
POST /api/v1/books/{book_id}/scenes/{scene_id}/generate
```

生成接口创建任务后立即返回 `task_id`，后台异步执行。

### 查询接口

```text
GET /api/v1/books/{book_id}
GET /api/v1/scenes/{scene_id}/plan
GET /api/v1/scenes/{scene_id}/drafts
GET /api/v1/scenes/{scene_id}/drafts/{draft_id}
GET /api/v1/scenes/{scene_id}/quality-report
GET /api/v1/scenes/{scene_id}/memory-proposals
GET /api/v1/tasks/{task_id}
GET /api/v1/tasks/{task_id}/history
```

查询默认返回当前有效版本，旧版本必须明确指定。正文列表和状态历史支持分页。

### 任务动作

统一使用动作接口：

```text
POST /api/v1/tasks/{task_id}/actions
```

请求体示例：

```json
{
  "action": "skip_scene",
  "reason": "当前场次无法自动修复",
  "expected_state_version": 8
}
```

支持动作：

```text
pause
resume
cancel
skip_scene
retry_planning
retry_writing
retry_technical_call
```

记忆人工确认：

```text
POST /api/v1/memory-proposals/{proposal_id}/approve
POST /api/v1/memory-proposals/{proposal_id}/reject
```

所有状态修改必须带 `expected_state_version`。版本不一致返回 `VERSION_CONFLICT`，不覆盖最新状态。

所有生成任务必须带 `idempotency_key`。重复请求返回原 `task_id`，不创建第二个任务。

### 前端状态显示

前端只显示简化状态：

```text
规划中
生文中
审查中
处理中
等待确认
已暂停
已阻塞
已完成
已跳过
异常处理中
```

第一版使用定时查询，默认每2～5秒查询一次；任务完成、暂停或阻塞后停止轮询。

### 统一返回和错误

成功：

```json
{
  "request_id": "req_123",
  "data": {}
}
```

失败：

```json
{
  "request_id": "req_123",
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "任务状态已变化，请刷新后重试",
    "details": {}
  }
}
```

基础错误码：

```text
INVALID_INPUT
BRIEF_NOT_CONFIRMED
SCENE_ALREADY_RUNNING
TASK_BLOCKED
WAITING_CONFIRMATION
PERMISSION_DENIED
TECHNICAL_ERROR
VERSION_CONFLICT
```

## 八、检索和 ContextPack

检索属于上下文与数据管理，不新增 Retrieval Agent。

第一版流程：

```text
按作品、章节、场次、版本和权限筛选
  → 关键词检索
  → 向量检索
  → 去重和简单排序
  → 权限过滤
  → 冲突标记
  → 组装固定 ContextPack
```

资料层级：

1. 作品固定资料
2. 作品动态资料
3. 章节和场次资料
4. 一般参考资料

优先级：

```text
CreativeBrief
  → 正式世界规则
  → 已确认作品记忆
  → 本场和上一场最终状态
  → 章节摘要和前文
  → 一般参考资料
```

不同 Agent重点读取不同资料：

- 规划：Brief、章节目标、前后场状态、人物和世界规则。
- 生文：ScenePlan、上一场最终状态、人物、地点、正式规则、前文必要片段、风格要求。
- 审查：ScenePlan、ProseDraft、正式规则、人物设定、前后场状态和章节资料。
- 记忆：审查通过正文、QualityReport和当前正式记忆。

ContextPack必须记录：

- 资料来源编号
- 来源版本
- 选择原因
- 排除资料
- 缺失资料
- 冲突标记
- 组装时间
- 快照哈希

第一版暂不做 Agent自主多轮检索、自动学习检索权重、图数据库推理和自动判断规则可信度。

## 九、模型路由和 API 切换

第一版使用个人硅基流动 API 和 DeepSeek完成全链路测试。规划、生文、三位审查员和记忆提取可以先使用同一个模型。

每场按约1250字的正式标准测试，建议范围1000～1500字。

正式长文质量和规模测试时增加公司中转站 API。切换只修改 Harness 模型路由配置，不修改 Agent、接口、数据库和流程。

Agent只提交任务类型，例如：

```text
planning
writing
review_world
review_plot
review_style
memory_extraction
arbiter
```

Harness根据任务类型选择模型档案。模型档案包括：

- 供应商
- 模型名称
- API 地址引用
- 超时时间
- 技术重试次数
- 最大输出长度
- 预算限制
- 提示词版本

模型调用独立隔离：

- 不共享聊天上下文
- 不共享隐含会话
- 三位审查员不读取其他审查员结果
- 每次调用有独立 `harness_call_id`

技术失败处理：

```text
超时或接口失败
  → 同一任务技术重试
  → 备用模型或供应商
  → 异常队列
```

技术故障不增加内容返工次数。Harness收到响应后先做 Contract格式校验，校验通过才交给下一个节点。

API 密钥不直接写入业务数据库或文档，只配置在本地环境变量或密钥管理中。

第一版暂不做自动学习路由、动态成本优化和 Agent自主选择模型。

## 十、前端和管理后台

同一个前端项目分为：

```text
创作工作台
管理后台
```

创作工作台：

- 作品和章节
- CreativeBrief
- 场次任务
- 简化流程状态
- 正文和版本
- 审查报告
- 记忆提案
- 人工确认
- 异常处理

管理后台：

- 用户和角色
- 作品访问范围
- 模型 API配置
- Harness路由
- 调用记录和错误日志
- 异常队列
- 任务强制暂停、恢复和取消
- 备份状态

管理后台不直接编辑正文和正式世界规则。

## 十一、权限方案

第一版四类角色：

### 创作人员

可以创建作品、提交 Brief、发起任务、查看结果、暂停和恢复普通任务、发起重新规划和重新生文。

不能确认正式世界规则、写入公共图书馆、修改已确认 Brief或直接修改正式记忆。

### 审核人员

可以查看审查报告、确认或拒绝记忆提案、处理阻塞任务、确认跳过场次、查看完整版本和状态历史。

### 系统管理员

可以管理用户、角色、作品访问范围、模型 API、Harness路由、系统参数、技术异常、备份和恢复。

默认不负责确认小说内容。

### 只读人员

只能查看作品、规划、正文、审查报告、记忆提案、任务状态和异常记录。

权限规则：

- 默认拒绝。
- 按作品范围隔离。
- 所有权限在统一后端校验。
- 所有关键写入记录操作者、时间、前后版本和原因。
- Agent不是普通用户角色，只能通过后端读 ContextPack和提交 Contract结果。

## 十二、备份和恢复

第一版采用：

```text
每日自动备份
+ 关键操作前手动备份
+ 真实恢复测试
```

需要备份：

- 业务数据库
- Harness调用记录
- 模型路由配置
- 审查规则
- 状态枚举
- 数据库结构版本
- 检索配置

频率：

- 每日一次完整备份
- 数据库结构变更前备份
- 正式长文测试前备份
- CreativeBrief确认和正式规则写入前备份

保留周期：

- 最近7天每日
- 最近4周每周
- 最近3个月每月

恢复层级：

1. 单条数据或历史版本
2. 单场或单章
3. 整库

备份状态：

```text
backup_running
backup_success
backup_failed
restore_testing
restore_success
restore_failed
```

备份失败自动重试一次，仍失败进入异常队列并在管理后台显示。

每月在隔离环境进行一次真实恢复测试。初始目标：

- `RPO ≤ 24小时`
- `RTO ≤ 4小时`

第一版暂不做实时多机复制、跨地域容灾、自动故障切换和秒级恢复。

## 十三、第一版验收方案

系统逻辑验收使用固定模拟响应，真实模型验收使用硅基流动 DeepSeek。

### 12个系统逻辑样例

1. 正常完成一场。
2. 普通局部问题不超过10个，返回生文。
3. 普通问题超过10个，升级严重并调用裁决。
4. 普通问题但影响跨场，调用裁决。
5. 三位审查员对同一事实给出相反结论，调用裁决。
6. 连续三次正文不合格，第三次返回规划。
7. 规划返工后仍不合格，场次阻塞并暂停小说。
8. 模型超时或结果未知，进入异常队列，技术重试不增加内容次数。
9. 场景事实自动保存、正式规则等待人工确认、冲突提案不自动写入。
10. 重复点击生成只返回原任务。
11. 跳过阻塞场次，连续性缺口进入下一场 ContextPack。
12. 旧页面提交操作时返回 `VERSION_CONFLICT`，不覆盖最新状态。

### 真实模型测试

- 使用硅基流动 DeepSeek。
- 连续测试3～5场。
- 每场约1250字。
- 至少覆盖正常场、返工场和记忆提案场。
- 正式长文测试时切换公司中转站。

### 通过标准

- 核心状态全部走通。
- 返工次数准确。
- 技术异常不混入内容失败。
- Contract版本关系正确。
- 下一场读取正确的最终状态。
- 待定提案不进入生文资料。
- Agent不能写正式世界规则。
- 关键人工操作有审计记录。
- 能从备份恢复单场旧版本并继续处理任务。

## 十四、分阶段开发计划

开发不是一次性完成，而是按 13 个阶段逐步验收。每个阶段完成后，必须满足完成标准，再进入下一阶段。阶段 1 已由新窗口完成。

### 阶段 1：固定 Contract 和状态枚举（已完成）

目标：把方案中的七类 Contract、字段类型、必填字段和状态名称变成机器可校验的规范。

要做：

- 定义七类 Contract 的 JSON Schema。
- 定义流程节点、任务状态、版本状态、审查、记忆和备份枚举。
- 明确 `contract_version` 和 `payload` 包络格式。
- 验证 JSON 语法、七类定义完整和核心字段覆盖。

输入：方案基线和字段边界规则。

输出：`contracts/contracts.schema.json`、`contracts/enums.json`、Contract使用说明。

完成标准：所有 Contract能通过 Schema校验；枚举没有同义重复；新增字段和枚举值有版本规则。

### 阶段 2：创建数据库表和迁移文件

目标：让 Contract、任务状态、版本和运行记录有稳定存储。

要做：

- 创建 `books`、`chapters`、`scenes`。
- 创建七类 Contract表。
- 创建 `task_events`、`exception_queue`、`harness_calls`、`memory_records`。
- 创建外键、版本唯一、幂等唯一和同场单任务约束。
- 创建数据库初始化和迁移文件。

输入：阶段 1 Schema、数据库逻辑结构和状态枚举。

输出：数据库迁移文件、初始化脚本、基础种子数据。

完成标准：数据库可以从空环境初始化；所有核心表可读写；旧版本不被覆盖；重复场次任务被拒绝。

### 阶段 3：统一后端任务状态控制

目标：实现唯一流程控制中心。

要做：

- 创建和读取 TaskState。
- 实现 `current_node`、`status`、`next_action`。
- 实现规划、生文、审查、裁决、记忆、人工确认和异常节点流转。
- 实现内容次数、技术重试次数和状态历史。
- 实现暂停、恢复、阻塞、完成、跳过和取消。

输入：数据库、状态枚举和主链路规则。

输出：任务状态服务、状态流转规则、状态事件记录。

完成标准：12个逻辑分支中的状态变化可以被固定测试；Agent不能直接写 TaskState。

### 阶段 4：REST 接口和统一错误格式

目标：让前端可以安全地创建任务、查询结果和发起人工动作。

要做：

- 实现 `/api/v1` 业务接口。
- 实现作品、Brief、场次任务和 Contract查询。
- 实现统一任务动作接口。
- 实现 `request_id`、`idempotency_key` 和 `expected_state_version`。
- 实现分页、版本指定和统一错误码。

输入：Contract Schema、TaskState服务和数据库。

输出：接口实现、接口说明和错误码表。

完成标准：重复请求不创建重复任务；过期状态返回 `VERSION_CONFLICT`；非法动作被拒绝。

### 阶段 5：Harness 和模型接口适配器

目标：统一管理模型调用，隔离供应商差异。

要做：

- 定义 Agent任务请求格式。
- 定义统一模型请求和响应格式。
- 实现供应商适配器接口。
- 实现超时、技术重试、备用模型和预算字段。
- 实现 Contract格式校验。
- 保存 `harness_calls`。

输入：任务类型、ContextPack引用和模型路由配置。

输出：Harness服务、模型适配器接口、调用记录。

完成标准：Agent不直接接触供应商 API；更换模型只需改配置；格式错误不会进入下一个节点。

### 阶段 6：接入硅基流动 DeepSeek

目标：使用低成本模型验证真实调用。

要做：

- 配置硅基流动 API 地址和密钥引用。
- 配置 DeepSeek模型档案。
- 为规划、生文、三位审查员和记忆提取配置任务类型。
- 验证独立请求和上下文隔离。

输入：Harness和模型适配器。

输出：本地开发模型配置，不把真实密钥写入代码或文档。

完成标准：能完成一次规划调用、正文调用和审查调用；每次调用有独立记录。

### 阶段 7：资料筛选、混合检索和 ContextPack

目标：按 Agent和节点生成固定、可追溯的资料包。

要做：

- 实现作品、章节、场次和版本筛选。
- 实现关键词检索。
- 实现向量检索。
- 实现去重、排序、权限过滤和冲突标记。
- 排除待定提案。
- 保存来源版本、排除项、缺失项和快照哈希。

输入：数据库、正式记忆资料和目标 Agent任务。

输出：ContextPack组装服务。

完成标准：同一版本输入能得到可复现快照；生文资料包不包含待定提案；资料冲突不会被静默合并。

### 阶段 8：实现四类业务 Agent

目标：把规划、生文、审查和记忆提取接入统一流程。

要做：

- 规划 Agent输出 ScenePlan。
- 生文 Agent输出约 1250 字 ProseDraft。
- 审查 Agent并行调用三位审查员。
- 记忆 Agent只在审查通过后输出 MemoryProposal。
- 裁决 Agent按严重、跨场和真正冲突规则按需调用。

输入：Harness、ContextPack和 Contract Schema。

输出：各 Agent实现、提示词版本和结果校验。

完成标准：Agent只读 ContextPack、只返回自身 Contract；三位审查员互不读取彼此结果。

### 阶段 9：创作工作台

目标：让创作人员和审核人员能完成日常操作。

要做：

- 作品和章节页面。
- CreativeBrief填写和确认。
- 场次生成和结果查看。
- 规划、正文、审查报告和记忆提案查看。
- 简化任务状态显示。
- 暂停、恢复、确认、拒绝和异常处理。

输入：REST接口和权限服务。

输出：创作工作台页面。

完成标准：用户无需接触内部 Agent状态；能看到“规划中、生文中、审查中、等待确认、已阻塞、已完成”。

### 阶段 10：管理后台

目标：让管理员管理系统运行，不直接参与正文创作。

要做：

- 用户和角色管理。
- 作品访问范围管理。
- 模型 API和 Harness路由管理。
- Harness调用记录和错误日志。
- 异常队列。
- 任务强制暂停、恢复和取消。
- 备份状态。

输入：权限服务、REST接口和运行记录。

输出：管理后台页面。

完成标准：普通用户不能进入管理操作；管理员不能绕过规则直接写正文和正式世界规则。

### 阶段 11：固定模拟响应和 12 个验收样例

目标：不依赖模型随机性，验证所有系统分支。

要做：

- 实现 MockModelAdapter。
- 准备固定规划、正文、审查和记忆响应。
- 依次执行正常、返工、裁决、阻塞、异常、权限、重复任务、跳过和版本冲突样例。
- 验证状态、版本、权限和数据写入结果。

输入：阶段 1～10 的系统实现。

输出：自动化验收脚本和测试报告。

完成标准：12个样例全部通过；每个失败都能定位到具体节点和事件。

### 阶段 12：真实模型测试

目标：验证真实 API、资料传递和基本正文质量。

要做：

- 使用硅基流动 DeepSeek连续测试 3～5 场。
- 每场目标约 1250 字，建议范围 1000～1500 字。
- 至少覆盖正常场、返工场和记忆提案场。
- 检查前后场状态、ContextPack、审查报告和版本关系。
- 记录成本、耗时和技术异常。

输入：通过的系统逻辑验收和硅基流动配置。

输出：真实模型测试报告。

完成标准：系统能连续处理场次，切换模型只改 Harness配置，未出现上下文串用或未授权写入。

### 阶段 13：备份恢复和方案完全落地验收

目标：证明系统不仅能运行，也能恢复和继续生产。

要做：

- 执行一次完整备份。
- 在隔离环境恢复数据库和 Harness调用记录。
- 恢复单条历史版本、单场任务和一个阻塞任务。
- 验证正文、审查报告、记忆和 TaskState关联。
- 从恢复环境继续处理一个任务。
- 输出最终验收报告。

输入：真实模型测试结果和备份配置。

输出：恢复测试记录、最终验收报告。

完成标准：12个逻辑样例通过；3～5场真实模型测试通过；备份恢复测试通过；权限、版本、异常和状态闭环均可审查。

### 方案完全落地的判断

必须完成第 13 阶段。第 10 阶段完成代表主要功能开发完成；第 11 阶段证明系统逻辑正确；第 12 阶段证明真实模型链路可用；第 13 阶段证明系统可恢复、可继续运行。只有第 13 阶段完成，才称为第一版方案完全落地。
